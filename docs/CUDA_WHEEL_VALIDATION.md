# Linux CUDA environment wheel validation

Both local CPython 3.12 Linux x86-64 wheels were installed into the separate
`venv312-cuda` environment on the i5-10400 / RTX 3070 host. Imports from `/tmp`
resolved to that environment's site-packages, not editable source checkouts.
The environment uses PyTorch 2.10.0+cu128 and torchvision 0.25.0+cu128.

The installed mask wheel passed all **139 tests** in 13.09 s, and the installed
dataset wheel passed all **157 tests** in 17.16 s, sequentially. Mask tests
include the four deterministic CPU model-update checks; running them inside a
CUDA-capable environment does not turn them into GPU training tests.

`validation/cuda-wheel-installed-audit-v1.json` records wheel SHA-256 values,
every archive member, and byte equality of installed Python sources, profiles,
and native libraries. Mask JUnit, the combined test log, and the build/install
log are retained beside it. Dataset JUnit is retained in the dataset repository.

The audit found six unwanted Python bytecode files in the dataset wheel. Python
may regenerate these after installation, so they are explicitly excluded from
the installed source/native byte-equality claim. The old wheel is retained as
the exact tested artifact. The rebuilt dataset v2 wheel excludes all six files,
passes RECORD and installed-byte checks, and preserves exactly the same Python
source/profile/native bytes as the 157-test CUDA installation. A separate new
Linux environment containing only its runtime dependencies passed Detect/Segment
cold/warm-cache parity and restored-mtime content-invalidation smoke checks.
The v1 rejection and v2 clean-install reports are in the dataset repository.
The CUDA training environment retains its original v1 wheels, preserving the
pilot's artifact identity. The mask
wheel contained no generated bytecode files. Notice-file inventory is included
in the audit, but completeness of third-party notices remains unproven.

These are unrepaired local `linux_x86_64` wheels. They do not prove manylinux,
Windows, other Python versions, standalone dependency installation, or release
readiness. The CPU benchmark environment was not converted to CUDA.

## Actual GPU training trial

`bench/train_coco_gpu.py` runs the actual SegmentationTrainer with random
YOLO11n-seg weights, FP32, SGD, 640-pixel images, and every image in the fixed
5,000-image COCO fixture. Train and validation reuse that fixture, so this is
not an accuracy experiment. Reference, mask-only, and combined replacements are
explicit separate processes. The first completed pilot uses combined replacement,
workers 0, batch 4, and one full epoch; it is not a repeated comparison.

`bench/results/cuda-training-both-w0-pilot-v1.json` has `complete=true`: all
5,000 images / 1,250 batches finished with finite losses, positive mean
segmentation loss, a changed model state and no OOM retry. The training epoch
took **156.77 s (31.89 images/s)**. Whole-job time was **298.05 s**, including
setup, normal validation/checkpoint/final-validation work; imports and fixture
preflight are outside this timer. CUDA allocator peaks were 1,614,308,864 bytes
allocated and 2,898,264,064 bytes reserved. The first run downloaded an Arial
font during final validation; that log is retained. This preparation run must
not be mixed into a subsequent repeated comparison or used to claim a speedup.

The trial records resolved settings, upstream training source hashes, installed
wheel runtime hashes, all batch loss components, initial/final model hashes,
CUDA allocator peaks and sampled process-family RSS. Epoch timers synchronize
CUDA only at their boundaries; they exclude setup, validation and checkpoint
saving. Whole-job time includes those stages. The first epoch includes GPU
warmup. Upstream prefetch may start during loader construction. External logger
and analytics callbacks are disabled. Both train and validation retain the
normal model/loss algorithms and local validation/checkpoint behavior.

Only a report with `complete=true`, 5,000 images per epoch, the expected batch
count, finite losses, changed model state and no OOM retries is a successful
trial. Five alternating independent pairs per frozen configuration, uncertainty
intervals, and separate correctness evidence are still required before making
training speedup claims.
